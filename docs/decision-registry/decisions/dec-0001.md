## Context

A multi-repo development approach was considered that involves disparate repositories for different components (e.g., separate repos for backend, frontend, infrastructure, and documentation). However, the goal is to streamline development, collaboration, and user experience by choosing an optimal repository strategy. Therefore, after consideration, it was determined that the _multi-repo_ approach would lead to several challenges, including:

- Difficulty for new users/contributors to onboard and understand the complete project landscape.
- Increased overhead in managing multiple repositories (permissions, branching strategies, CI/CD pipelines).
- Challenges in ensuring atomic changes across dependent components (e.g., a backend API change requiring a frontend update).
- Lack of a centralized source of truth for all project-related information.

Two options were considered:

- a monorepo (single repository)
- a multi-repo (separate repositories for each component).

The proposed decision is to adopt a monorepo strategy to centralize all codebases (.NET, JavaScript, Terraform) and documentation into a single repository to simplify access and management for users and developers.

---

## Options Considered

### Monorepo

**Description:** Consolidate all .NET code (e.g., API, services), JavaScript code (e.g., frontend, utilities), Terraform code (e.g., Azure infrastructure definitions), and all project documentation (e.g., Markdown files, architecture diagrams) into a single Git repository.

**Pros:**

- **Simplified Onboarding:** Users only need to clone one repository to access all project components and documentation, making it significantly easier for new team members to get started.

- **Atomic Changes & Consistency:** Facilitates atomic commits across different components (e.g., a backend API change and its corresponding frontend consumer update can be committed together). This ensures consistency and reduces integration issues.

- **Centralized Source of Truth:** All project-related assets are in one place, making it easier to find information and understand dependencies.

- **Simplified Versioning:** Easier to manage versions of related components. A single commit ID can represent the state of the entire project.

- **Enhanced Code Sharing:** Promotes code sharing and reuse across different parts of the application (e.g., shared utility libraries).

- **Streamlined CI/CD:** Potential for unified CI/CD pipelines that can build, test, and deploy multiple components within a single pipeline, although more complex to configure initially.

- **Easier Refactoring:** Refactoring code across different components becomes simpler as all code is locally available.

- **Documentation:** Improved discoverability of documentation.

**Cons:**

- **Larger Repository Size:** The repository can grow very large over time, potentially impacting clone times and local disk space.

- **Increased Build Times:** Full builds of the entire monorepo can be slow, requiring intelligent build tooling (e.g., caching, incremental builds) to mitigate.

- **Potential for Coupled Deployments:** Changes in one component might trigger builds and tests for unrelated components, increasing CI/CD complexity if not managed well with intelligent tooling.

- **Tooling Complexity:** Requires robust tooling for managing dependencies, running selective builds, and enforcing code ownership (e.g., using CODEOWNERS).

- **Branching Strategy Complexity:** Managing branches (e.g., feature branches, release branches) can become more complex with a large number of contributors.

- **Security Concerns:** A single breach could expose all project code.

- **Coupling:** Risk of tight coupling between components.

- **Increased Complexity:** Increased complexity in managing build tools for diverse tech stacks.

### Multi-repo

**Description:** Separate repositories for .NET, JavaScript, Terraform, and documentation.

**Pros:**

- **Segregation:** Clear separation of concerns.

- **Access Control:** Easier access control per repo.

- **Coupling:** Reduced risk of unintended coupling.

- **Smaller Repository Size:** Each repository is smaller, leading to faster clone times.

- **Independent Deployments:** Each component can be deployed independently, allowing for more granular release cycles.

- **Clearer Ownership:** Easier to define clear ownership for each repository.

- **Simpler CI/CD (Per Repo):** CI/CD pipelines are typically simpler to set up for individual repositories.

**Cons:**

- **Documentation:** Documentation may be harder to find or maintain.

- **Complex Onboarding:** New users need to clone multiple repositories, understand their interdependencies, and set up multiple development environments.

- **Version Mismatch Issues:** Difficult to ensure compatible versions across dependent components, leading to "works on my machine" issues.

- **Increased Management Overhead:** More repositories to manage (permissions, hooks, settings).

- **Reduced Visibility:** Difficult to get a holistic view of the entire project.

- **Cross-Repository Atomic Changes are Hard:** Making a change that spans multiple repositories requires coordinating multiple commits and pull requests.

- **Duplication of Code/Configuration:** Tendency to duplicate common libraries or CI/CD configurations across repositories.

## Evaluation Criteria

The decision was evaluated based on the following criteria:

- **Ease of Use:** How simple it is for developers and users to access and work with the codebase and documentation.
- **Collaboration:** Support for cross-functional team collaboration across .NET, JavaScript, Terraform, and documentation.
- **CI/CD Simplicity:** Ease of setting up and maintaining continuous integration/continuous deployment pipelines.
- **Scalability:** Ability to handle future growth in codebase size and team size.
- **Dependency Management:** Simplification of managing dependencies across different components.
- **Maintainability:** Ease of maintaining consistent versioning, documentation, and code quality.

---

## Decision

The Monorepo strategy aligns better with [evaluation criteria](#evaluation-criteria). The benefits of simplified onboarding, atomic changes, and centralized access to all code and documentation (including Terraform) directly address your pain points and desired user experience. While there are challenges associated with monorepos (size, build times, CI/CD complexity), these are acceptable tradeoffs for this particular project ([Offgrid](https://github.com/drminnaar/offgrid)).The cohesive nature of a monorepo will ultimately provide a more unified development and user experience for the project.

### Rationale

The monorepo strategy was chosen for the following reasons:

- **Ease of Use:** A single repository simplifies the onboarding process for developers and users, requiring only one git clone to access all project components (.NET, JavaScript, Terraform, documentation).

- **Collaboration:** Centralizing all components fosters better collaboration across teams (e.g., backend, frontend, DevOps, and documentation writers) by providing a unified view of the project.

- **Unified CI/CD:** A monorepo allows for a single CI/CD pipeline configuration, reducing overhead and ensuring consistent builds and deployments across components.

- **Dependency Management:** Shared dependencies (e.g., libraries or configurations) are easier to manage in a monorepo, reducing version mismatches and simplifying updates.

- **Documentation Integration:** Keeping documentation alongside code ensures it remains up-to-date and easily discoverable, addressing the goal of user-friendliness.

---

## Implications

- **Development Workflow:** Developers will work in a single repository, reducing context-switching but requiring adherence to monorepo best practices.

- **CI/CD Pipeline:** A unified pipeline will be implemented, potentially using tools like GitHub Actions or GitLab CI, with separate jobs for .NET, JavaScript, Terraform, and documentation.

- **Team Collaboration:** Cross-functional teams will benefit from centralized code and documentation, but clear ownership of components must be defined.

- **Tooling Investment:** Initial setup of monorepo tooling may require time, but long-term benefits include streamlined workflows.
