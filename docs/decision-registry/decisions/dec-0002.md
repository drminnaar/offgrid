## Context

- The software team is managing a monorepo that contains:
  
  - Backend code: APIs and background workers.
  - Frontend code: React and Next.js applications.
  - Infrastructure code: Terraform for provisioning and managing cloud resources.
  - CI/CD: Using GitHub Actions for automation, hosted on GitHub.

- The team requires a branching strategy that:

  - Supports a monorepo with multiple project types (backend, frontend, infrastructure).
  - Enables efficient collaboration across team members working on different components.
  - Facilitates continuous integration and deployment (CI/CD) with GitHub Actions.
  - Ensures stability for production releases while allowing rapid development and testing.
  - Handles versioned releases and potential hotfixes for APIs or infrastructure.

Four branching strategies were evaluated:

- **Git Flow:** A highly structured model designed for projects with distinct, versioned releases, emphasizing long-lived branches for development and formal release management
- **GitHub Flow:** A lightweight, branch-based workflow centered on continuous delivery and rapid iteration, where the primary development branch is consistently deployable.
- **GitLab Flow:** A hybrid approach that simplifies Git Flow by working directly with the main branch while incorporating environment-specific branches for controlled, downstream deployments and integrating with issue tracking.
- **Trunk-Based Development:** A practice focused on frequent, small merges directly to a single main branch, prioritizing continuous integration and immediate deployability.

---

## Options Considered

### Git Flow

**Description:** A structured branching model with multiple long-lived branches: `main (production)`, `develop (integration)`, `feature/* (new features)`, `release/* (pre-release preparation)`, and `hotfix/* (urgent fixes)`. Features are developed in isolated branches, integrated into develop, and then merged into main via release branches.

**Pros:**

- Well-suited for large teams and complex projects with scheduled release cycles.
- Clear separation of development stages (feature, integration, release, hotfix).
- Supports versioned releases, which is useful for APIs requiring specific versions.
- Isolates experimental work, ensuring main remains stable.

**Cons:**

- Complex, with multiple long-lived branches, leading to overhead in branch management.
- Slower release cycles due to the need for release branches and thorough testing.
- Challenging to integrate with continuous deployment (CD) in a monorepo, as coordinating releases across backend, frontend, and Terraform is tedious.
- Higher risk of merge conflicts due to long-lived feature branches.
- Less compatible with GitHub Actions’ focus on rapid, automated deployments.

### GitHub Flow

**Description:** A lightweight strategy with a single main branch for production-ready code and short-lived `feature/*` branches that are merged into `main` after review and testing. Emphasizes continuous delivery.

**Pros:**

- Simple and agile, ideal for small teams or projects with frequent deployments.
- Aligns well with GitHub Actions for automated testing and deployment on every merge to main.
- Reduces branch management overhead, suitable for a monorepo with multiple components.
- Encourages rapid iteration and deployment, fitting well with React/Cluster.js development cycles.

**Cons:**

- Lacks support for versioned releases or multiple environments (e.g., staging, production) without additional branches.
- May lead to less stable main branch if testing is not rigorous, risky for Terraform or backend APIs.
- Not ideal for projects requiring hotfixes or maintaining multiple API versions.
- Limited structure for complex monorepo workflows with interdependent backend, frontend, and infrastructure changes.

### GitLab Flow

**Description:** A hybrid approach combining GitHub Flow’s simplicity with environment-specific branches (e.g., staging, production). Features are developed in short-lived feature/* branches, merged into main (often representing staging), and then into a production branch for release. Supports versioned releases and hotfixes via release branches.

**Pros:**

- Balances simplicity and structure, suitable for monorepos with multiple components (backend, frontend, Terraform).
- Supports multiple environments (e.g., staging, production), aligning with the need for stable API and infrastructure deployments.
- Facilitates versioned releases and hotfixes, critical for APIs and Terraform configurations.
- Compatible with GitHub Actions for CI/CD, using path-based triggers to build/test only changed components in the monorepo.
- Integrates issue tracking and code reviews, ensuring quality before merging.

**Cons:**

- Slightly more complex than GitHub Flow due to additional environment branches.
- Requires discipline to maintain branch hygiene and avoid long-lived branches.
- Less familiar to teams accustomed to GitHub Flow, requiring some onboarding.

### Trunk-Based Development

**Description:** Uses a single trunk (or main) branch where all changes are committed directly or via very short-lived feature branches. Emphasizes frequent integration and relies heavily on automated testing for stability.

**Pros:**

- Simplest branching model, minimizing merge conflicts and branch management.
- Encourages continuous integration, aligning well with GitHub Actions for rapid builds and deployments.
- Ideal for monorepos, as it simplifies dependency management across backend, frontend, and Terraform code.
- Promotes fast feedback loops, suitable for agile React/Cluster.js development.

**Cons:**

- Requires extremely robust automated testing to prevent unstable code in trunk, which may be challenging for Terraform or complex APIs.
- Lacks built-in support for versioned releases or multiple environments without additional tooling.
- Not ideal for hotfixes or maintaining multiple API versions, critical for backend stability.
- May overwhelm less experienced teams due to the need for frequent commits and strong CI/CD discipline.

## Decision

Adopt GitLab Flow as the Git branching strategy. It encourages a balanced approach, combining the agility of feature branching with structured environment promotion. Additionally, it aligns well with the need for controlled deployments across diverse codebases, especially for Terraform.

### Rationale

GitLab Flow is selected because it best aligns with the team’s requirements for managing a monorepo containing backend (APIs, background workers), frontend (React, Next.js), and Terraform code, while using GitHub and GitHub Actions for CI/CD. The key reasons are:

- Support for Multiple Environments: GitLab Flow’s use of environment-specific branches (e.g., staging, production) ensures stable deployments for backend APIs and Terraform infrastructure, which require thorough testing before production. This addresses the limitations of GitHub Flow, which assumes immediate deployment to production.

- Monorepo Compatibility: GitLab Flow works well with monorepos by allowing selective CI/CD triggers (e.g., using GitHub Actions’ path filtering) to build/test only changed components (e.g., backend, frontend, or Terraform). This reduces build times and optimizes resource usage.

- Versioned Releases and Hotfixes: GitLab Flow supports release branches (e.g., v1, v2) and hotfixes, critical for maintaining stable APIs and Terraform configurations that may need to support multiple versions or urgent fixes.

- CI/CD Integration: GitLab Flow integrates seamlessly with GitHub Actions, leveraging workflows to automate testing, building, and deployment for each environment branch. Path-based triggers ensure efficient handling of monorepo changes.

- Balance of Simplicity and Structure: Unlike Git Flow’s complexity, GitLab Flow keeps branch management manageable while providing more structure than GitHub Flow or Trunk-Based Development, fitting the team’s need for collaboration and stability across diverse components.

- Alignment with Team Preference: The technical lead’s preference for GitLab Flow aligns with its ability to handle the project’s complexity while maintaining agility.

### Why Not Other Options?

- **Git Flow:** Too complex for a monorepo with frequent deployments, and its long-lived branches hinder continuous delivery. It’s better suited for traditional, large-scale projects with rigid release schedules.

- **GitHub Flow:** Too simplistic for managing multiple environments or versioned API releases, risking instability in production for backend and Terraform code.

- **Trunk-Based Development:** While simple and fast, it lacks native support for environment-specific branches and versioned releases, requiring significant additional tooling to meet the team’s needs for stable APIs and infrastructure.

---

## Implications

- **Positive:**

  - Streamlined CI/CD pipelines using GitHub Actions with path-based triggers for monorepo efficiency.
  - Clear separation of staging and production environments, ensuring stable releases for APIs and Terraform.
  - Support for versioned releases and hotfixes, critical for backend and infrastructure stability.
  - Simplified collaboration across backend, frontend, and infrastructure teams within the monorepo.

- **Negative:**

  - Requires team training on GitLab Flow, as it’s less common in GitHub-centric workflows.
  - Additional environment branches (staging, production) introduce slight overhead compared to GitHub Flow.
  - Need to maintain branch hygiene to avoid stale branches in the monorepo.
